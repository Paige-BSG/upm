This page is the **intended** design for UPM. No product source code has been released
into this public repository yet, so treat this as the direction, not a description of a
shipped artifact.

## The core idea

UPM manages databases and middleware on Kubernetes with an **in-product agent as a
first-class operator**. A human expresses intent; the agent plans; a domain harness
(security contract) gates it; deterministic operators make the change. The control plane
is deterministic because the thing that changes data is always a real operator, never the
agent acting through a shell.

## Three layers

1. **Agent / intent** — an in-product agent built on the **Pi Agent** runtime
   (`earendil-works/pi`, MIT). It provides the agent loop, tool calling, message/state and
   event streaming, and an abstract model layer (`@earendil-works/pi-ai`) so UPM is not
   bound to one model. Importantly, UPM does **not** reuse the coding agent's `bash`,
   file, and process permissions in production: in-product the agent sees only the
   minimal, low-privilege domain tools the harness exposes.

2. **Domain harness (spelled by UPM)** — the security contract around intent: typed
   database / Kubernetes tools, a realtime fact snapshot of the target, permissions,
   risk-tiering, approval, idempotency, timeouts, evidence, and audit. The agent reasons
   and orchestrates; the harness enforces boundaries. It is the boundary that keeps the
   agent from reaching a kubeconfig, a shell, or raw database credentials directly.

3. **Deterministic execution** — the code that actually carries out backup, restore,
   failover, and upgrade. In Phase 1 this is a narrow adapter over an **external** operator
   ([`@kubernetes/client-node`](https://github.com/kubernetes-client/javascript)) — not
   UPM's own controller. UPM's own deterministic code is TypeScript on Node 22. See
   [Phase 1 — BackupProof](/architecture/phase-1-backupproof).

## Boundaries

- **Adopt Pi runtime, not Pi coding-agent permissions.** Pi's core has no built-in
  permission system; it inherits the launcher's. UPM therefore provides the production
  permission model in its harness; in-product the agent defaults to the smallest-scoped
  domain tools, not cluster-admin access.
- **The first proof is Phase 1 — BackupProof** (Spec v0.2): the agent → plan → signed
  approval → backup → isolated restore → evidence loop on these three layers. It is a
  product technical validation, not a release or production high availability.
- **Security boundaries.** The agent has no `bash`, `kubectl`, `kubeconfig`, or database
  admin access. The adapter ServiceAccount is scoped to the designated namespace and the
  Percona CR. Approval is a **signed one-time token bound to `planHash`** that expires
  after 15 minutes; drift fails closed (`TARGET_DRIFTED_DURING_OPERATION`); `operationId`
  is idempotent; the journal is an immutable hash chain.
- **Data plane is a candidate.** Phase 1 drives an **external** Percona Server for MySQL
  Operator (non-PXC, group replication) plus Percona Server 8.4.10-10.1, XtraBackup, and
  MinIO. These are not UPM source; the operator tag commit, `ps.percona.com/v1` / kinds,
  the CRD bytes/SHA-256, and the per-arch image digests are recorded first-hand, and the
  remaining open items are the test-machine arch / compatibility, the MinIO image digest,
  the PS / XtraBackup license classification, and the client-node vs k8s pairing.
- **BackupProof is a versioned API / JSON Schema**, not a universal DSL. No UPM CRD is
  frozen by this page.
- Future components (the specific CRDs and manifest shapes) are **not** fixed by this
  page. They are decided in later phases and recorded here only once agreed; the design
  holds today, the component names do not.
