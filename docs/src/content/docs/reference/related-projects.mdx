UPM is an AI-native rebuild, but it is not developed in isolation. Two public projects
anchor it: one for the problem space, and one as a neutral comparison baseline.

## upmio

- Repository: [https://github.com/upmio](https://github.com/upmio)
- Role: **problem-space and operator-experience reference**. Our company already ships a
  data-service ops product, and this is its public repository. UPM uses it to understand
  the workflows, the pain points, and how operators approach the problem. It is **not**
  source code being moved into this repository; it is public reference material only.

## KubeBlocks

- Repository: [https://github.com/apecloud/kubeblocks](https://github.com/apecloud/kubeblocks)
- Role: **neutral comparison baseline**. KubeBlocks is a well-known open-source project in
  the same space. UPM records its OSS / Enterprise distinction as a fact, not as a
  criticism: the Open Source tier provides the control plane and Day-2 operations with
  official user documentation; the Enterprise tier is a separate commercial layer adding a
  management console, multi-tenancy and security auditing, additional commercial database
  engines, and cross-region DR and observability.
- UPM is an **AI-native alternative** to KubeBlocks, not a redeployment of it. The
  comparison is recorded neutrally in the agent LLM wiki, at the repo file
  `llm-wiki/wiki/comparisons/kubeblocks.md`, sourced from the vendor's own pages.

## The documentation stack

- **Nimbus Docs** ([`cloudflare/nimbus`](https://github.com/cloudflare/nimbus)) — the docs
  framework this site is built on. It is a meta-tool of this repository, not UPM tech
  stack, and is described in the LLM wiki.
- **Pi Agent** ([`earendil-works/pi`](https://github.com/earendil-works/pi), MIT) — the agent
  runtime the in-product agent is built on. It is UPM's product stack and is recorded in
  the LLM wiki (pinned to `v0.84.3`).
- **Kubernetes Client Node**
  ([`@kubernetes/client-node`](https://github.com/kubernetes-client/javascript), Apache-2.0) —
  the narrow Kubernetes client the Phase 1 deterministic execution layer drives the external
  operator through; UPM's own code is TypeScript on Node 22, not a shell or cluster-admin.
  Recorded in the LLM wiki pinned to `2.0.0`.

## Phase 1 data-plane candidate

The Phase 1 backup/restore slice drives an **external** data plane, not UPM source. These
are recorded in the LLM wiki as `candidate/pending admission`. The operator tag commit, the
`ps.percona.com/v1` API and its kinds, the CRD bytes/SHA-256, and the per-arch image digests
are recorded first-hand; still pending are the test-machine architecture / compatibility, the
MinIO image digest, the PS / XtraBackup license classification, and the official client-node
vs k8s pairing:

- **Percona Server for MySQL Operator** (v1.2.0, non-PXC, group replication) —
  [`percona-server-mysql-operator`](https://github.com/percona/percona-server-mysql-operator).
- **Percona Server for MySQL** (8.4.10-10.1) —
  [`percona-server`](https://github.com/percona/percona-server).
- **Percona XtraBackup** — [`percona-xtrabackup`](https://github.com/percona/percona-xtrabackup).
- **MinIO** — [`minio`](https://github.com/minio/minio).

None of these imply UPM itself is written in Go; the Operator's Go images are external
software. UPM's own Phase 1 code is TypeScript on Node 22.

**Future.** For UPM's own Rust operator, the client library is released as
[`kube-rs`](https://github.com/kube-rs/kube-rs) (Apache-2.0); Rust enters the stack once
UPM ships its own reconcile / finalizer / leader-election operator.
